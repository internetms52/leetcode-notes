# LinkedIn Zip Solver

## 遊戲規則

LinkedIn Zip 是 LinkedIn 推出的每日益智遊戲。

- 棋盤為 N×M 的格子盤
- 盤面上有數個編號節點（1, 2, 3, ...），稱為 ZipNode
- 玩家需要畫一條路徑，依序經過所有編號節點（1 → 2 → 3 → ...）
- 路徑只能上下左右移動，不能斜走
- 路徑必須覆蓋棋盤上的**每一個格子**，不能有空白
- 路徑不能重複經過同一個格子
- 路徑不能在抵達終點節點前穿越其他 ZipNode

---

## 解法說明

### 資料結構

| 類別 | 說明 |
|------|------|
| `LinkedinZipGame` | 棋盤資訊：寬、高、ZipNode 列表 |
| `ZipNode` | 編號節點：order、x、y 座標 |
| `Node` | 路徑中的一般格子：x、y 座標 |

### 解題流程

解法分為兩個階段：

#### 階段一：預先產生每段的所有可能路徑（LinkedinZipPathTreeGenerator）

將整條路徑拆分成 N-1 段，每段為相鄰兩個 ZipNode 之間（order i → order i+1）。

對每一段執行 DFS，列舉所有合法的簡單路徑：
- 不能超出棋盤邊界
- 不能重複走同一格
- 不能穿越不屬於該段的其他 ZipNode（剪枝）

每段產出 `List<LinkedList<Node>>`，代表所有可能的走法。

#### 階段二：Backtracking 組合各段路徑（LinkedinZipSolver）

從第一段開始，依序嘗試每一段的候選路徑：
1. 檢查候選路徑的節點是否與已走過的格子碰撞
2. 沒有碰撞則加入當前解，繼續往下一段探索
3. 若下一段無解則回溯，移除當前段，嘗試下一個候選路徑
4. 所有段都完成後，驗證解的節點總數等於 `width × height`（填滿棋盤）
5. 通過驗證則回傳完整解，否則繼續回溯

## Big-O 分析

### 符號定義

| 符號 | 說明 |
|------|------|
| W | 棋盤寬度 |
| H | 棋盤高度 |
| K | ZipNode 數量 |
| P | 每段的平均候選路徑數 |

### 時間複雜度

**階段一：路徑產生（每段）**

每段 DFS 在最壞情況下會遍歷棋盤上所有格子的排列，時間複雜度為：

```
O((W×H)!)  — 理論上界
```

實際上因為 ZipNode 的剪枝（不能穿越其他節點），可行路徑數遠小於此值。

**階段二：Backtracking**

共 K-1 段，每段最多嘗試 P 條候選路徑，碰撞檢查為 O(W×H)：

```
O(P^(K-1) × W×H)
```

**整體：**

```
O((W×H)! × K + P^(K-1) × W×H)
```

### 空間複雜度

| 項目 | 複雜度 |
|------|--------|
| 每段路徑儲存 | O(P × W×H) |
| 所有段路徑儲存 | O(K × P × W×H) |
| DFS 遞迴堆疊 | O(W×H) |
| Backtracking visited 集合 | O(W×H) |

**整體空間複雜度：**

```
O(K × P × W×H)
```

## 檢討

### 兩階段解法的問題

#### 記憶體浪費

兩階段解法在階段一會把每段所有可能路徑全部生成並存入 `List<List<LinkedList<Node>>>` 中，每條路徑都是一個完整的 `LinkedList<Node>`，全部同時活在記憶體裡。

空間複雜度為 `O(K × P × W×H)`，而 P（每段的候選路徑數）在稍大的棋盤上可能非常大。

#### 剪枝太晚

階段一的 DFS 不知道其他段選了什麼路，因此生成了大量「孤立來看合法，但與其他段組合後會碰撞」的路徑。這些路徑生成完才在階段二被拋棄，等於做了無效的計算。

---

### 單一 DFS 為何更好

#### 記憶體

只維護一條當前路徑 `path` 和一個 `visited` 二維陣列，空間複雜度降為 `O(W×H)`，固定且不隨路徑數增長。

#### 即時剪枝

走每一步之前就能立刻判斷：
- 這格有沒有走過（`visited`）
- 這格是否為 ZipNode，order 是否符合當前順序

不符合就立刻停，不會繼續往下展開。剪枝發生在最早的時間點，浪費的計算最少。

#### 一句話總結

> 兩階段是「先窮舉，再篩選」；單一 DFS 是「邊走邊剪」，永遠不會對一條注定失敗的路徑多走一步。
